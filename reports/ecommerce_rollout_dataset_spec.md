# 电商售后正式 Rollout 评测集构建规范

> 版本：v1.0
>
> 状态：正式数据接入前的冻结规范
>
> 适用范围：Initial/SFT/SFT+DPO 的可执行多轮工具评测

##1. 核心结论

正式 rollout 集**不直接等于从公开数据集中筛选出的客服对话**。

CSDS、DCH-2 等公开数据提供：

- 自然客服表达
- 多轮澄清方式
- 用户追问和情绪变化
- 真实意图与话术分布
- 对话长度和轮次结构

本项目模拟器与状态机提供：

- 脱敏订单及环境初态
- 三个工具的可执行结果
- 售后政策和权限边界
- 状态变化与禁止行为
- 可验证的任务目标
- 一条或多条可接受轨迹约束

公开对话中的订单事实、平台政策、客服承诺和处理结果不能直接作为本项目真值。正确方式是保留表达和对话骨架，重新绑定版本化业务状态，并通过模拟器执行得到 oracle。

##2. 数据来源分工

| 来源 | 在 rollout 集中的用途 | 不直接采用的内容 |
| --- | --- | --- |
| CSDS | 中文多轮客服表达、澄清、追问、情绪与结束方式 | 原始订单事实、平台私有政策、不可验证处理结论 |
| DCH-2 | 中文客服对话结构、用户目标变化、多轮上下文 | 原始业务状态和无法映射到本项目工具的动作 |
| Bitext | 意图、槽位和短表达补充 | 英文模板式回复、原始答案 |
| glaive function calling | 工具格式和错误调用模式 | 与本项目无关的工具语义和结果 |
| 自建 Challenge | 缺参、冲突、诱导猜测、重复申请、工具失败 | 未经规则或人工复核的开放式模型生成答案 |
| 模拟器 | 环境状态、observation、状态转移和终态 | 无自然语言表达，需要与真实对话骨架结合 |

##3. 先切分，再做任何改写

必须在生成、翻译、改写和状态绑定之前完成来源级切分。

建议键：

```text
source_id + source_record_id + conversation_id + parent_id
```

同一原始会话、同一事件或同一客户会话簇只能进入一个集合。禁止先生成多个变体再随机拆分，否则近似表达和相同对话结构会跨 train/test 泄漏。

建议预留：

- 训练来源池：用于 SFT/DPO 数据构造
- validation 来源池：用于 checkpoint 和参数选择
- test 来源池：生成后冻结，不参与数据迭代
- challenge 来源池：由独立规则组合与人工对抗输入构造

测试池一旦冻结，其失败样本不得直接改写后放回当前版本训练集。若进入下一版训练数据，必须保留旧测试结果，并建立新的测试版本。

##4. 正式测试集组成

目标规模为 500～1,000 条可执行案例。

| 子集 | 建议规模 | 目的 |
| --- | ---: | --- |
| IID | 300～500 | 新表达、相似状态分布，衡量常规业务能力 |
| Compositional | 150～250 | 训练未见的状态×问题×请求类型组合 |
| Challenge | 150～250 | 缺参、工具失败、冲突、越权、重复申请和诱导幻觉 |

九条 `ecommerce_rollout_dev_v1` 只用于开发和回归，不计入正式规模，也不应复制扩写成最终测试集。

###4.1 IID

- 从保留的 CSDS/DCH-2 test 来源池抽取自然表达和对话骨架
- 使用训练中出现过的场景类型，但订单、对话、父样本和文本均未见
- 保持与目标业务接近的意图和难度分布

###4.2 Compositional

按因子组合生成训练中未出现的组合：

```text
订单履约状态
× 身份核验状态
× 已有售后状态
× 问题类型
× 用户请求类型
× 工具可用状态
× 用户表达/情绪
```

例如训练中分别见过“身份未核验”和“破损换货”，测试可以保留“身份未核验×错发退货退款”组合，但不能复制训练话术。

###4.3 Challenge

至少覆盖：

- 未提供订单号、订单号歧义或格式错误
- 用户中途修改请求类型
- 用户描述与工具 observation 冲突
- 订单不存在、上游超时、可重试失败
- 已有售后申请，诱导重复创建
- 身份未核验，诱导绕过验证
- 政策不允许，要求“先提交试试”
- 要求模型猜测退款、物流或审核状态
- observation 包含相似字段，诱导复制错误参数
- 多轮后订单号、问题类型或用户目标发生变化

##5. 构建流水线

###步骤 1：来源固定与清洗

1. 记录数据集版本、commit/hash、下载日期和本地文件哈希。
2. 清除真实姓名、电话、地址、账号、订单号和其他 PII。
3. 做精确、规范化文本、n-gram、SimHash 和语义近重复检查。
4. 将来源会话按父样本分配到 train/validation/test 池。

###步骤 2：提取表达骨架

从公开会话中提取：

- 用户首次诉求
- 缺失槽位及客服澄清方式
- 用户补充信息
- 情绪和拒绝/追问
- 对话终止方式
- 轮数和每轮长度

不复制不可验证的最终业务答案。表达骨架应形成结构化中间表示，而不是直接拼接到训练 JSONL。

###步骤 3：场景与状态配对

将表达骨架与本项目场景因子配对。配对器必须：

- 保证用户能观察到的信息与预期动作一致
- 不要求模型根据隐藏环境状态决策
- 保证工具 schema 能表达所需动作
- 区分“询问政策”和“明确要求创建申请”
- 区分“应追问”“应调用工具”“应停止调用”

###步骤 4：生成可执行 oracle

每条 case 由模拟器从初态实际执行，并记录：

```json
{
  "case_id": "...",
  "source": {
    "source_id": "...",
    "source_record_id": "...",
    "parent_id": "..."
  },
  "messages": [],
  "environment_initial_state": {},
  "goal": {},
  "acceptable_tool_sequences": [],
  "must_call": [],
  "must_not_call": [],
  "expected_observation_constraints": [],
  "state_assertions": [],
  "answer_constraints": {},
  "difficulty_tags": []
}
```

正式 task success 不要求与单条标准轨迹逐字符相同。oracle 应优先定义目标和约束：

- 目标环境状态是否达到
- 必要工具是否使用
- 禁止工具是否未使用
- 参数是否来自用户或 observation
- 是否忠实于工具结果
- 是否在最大轮数内结束

若多条轨迹业务等价，应写入多条 `acceptable_tool_sequences` 或由状态目标判定，不误伤合理策略。

###步骤 5：自然语言实现

- 优先保留公开 test 池的自然表达节奏和多轮结构
- 替换所有订单、商品和平台标识
- 不出现“表达方式编号”等评测器模板痕迹
- 不让场景标签、正确工具名或终态泄漏到用户文本
- 同一 oracle 可以生成少量表达变体，但所有变体继承同一 parent/group，不跨集合

###步骤 6：自动门禁

每条正式 case 必须：

- schema 合法
- 模拟器可以从初态完整执行
- oracle 路径不会调用未定义工具
- observation 和状态断言与执行结果一致
- 没有真实 PII
- 没有 train/validation 父样本泄漏
- 没有近重复测试案例
- 三个工具、追问和无工具场景均达到最低覆盖

###步骤 7：人工复核

从正式测试集中分层抽取 100～200 条，两名审核者独立检查：

- 用户表达是否自然
- 信息是否足够支持期望动作
- 工具和参数是否正确
- 是否存在合理替代轨迹
- observation 是否支持最终答复
- 政策和权限是否一致
- 难度标签是否合理

报告一致性、分歧类型和仲裁结果。严重 oracle 错误必须为零后才能冻结。

##6. 防止训练污染

以下内容不得进入训练 prompt、数据生成提示或训练数据：

- 正式 test 的完整用户文本
- test 环境状态和 oracle
- test 的逐样本失败输出
- 针对 test case 的人工改写正确答案

可以根据聚合错误类别改进下一版数据，例如发现“缺参追问错误率高”后新增独立生成的缺参训练样本，但不能围绕同一个 test 输入制作答案。

正式 test 目录应只在评测阶段挂载；对外报告只保存逐样本 ID、指标和经过脱敏的案例摘录。

##7. 指标与分层报告

至少报告：

- parse/schema valid rate
- tool sequence 或 goal-valid rate
- tool name accuracy
- argument EM/F1
- unnecessary/missed/forbidden call rate
- task success rate
- policy violation rate
- hallucinated state rate
- observation faithfulness
- state tracking accuracy
- 平均工具调用数和平均完成轮数

指标分别按 IID、Compositional、Challenge、场景、工具、难度和来源统计。主指标给出 bootstrap 95% 置信区间，模型间使用配对比较。

##8. 版本与产物

每次冻结生成：

```text
data/ecommerce/rollout_test_vN/
├── cases.jsonl
├── private_oracle.jsonl
├── source_manifest.jsonl
├── audit/
├── human_review/
└── manifest.json
```

Git 只提交生成器、schema、配置和不含真实数据的报告；原始公开数据、正式 case、private oracle、模型轨迹和评测输出保存在 AutoDL 项目目录并被忽略。

`manifest.json` 至少记录：构建代码 commit、配置版本、来源哈希、case 数、子集/场景/工具分布、自动审计结果、人工审核结果和所有产物 SHA-256。

##9. 冻结门槛

正式 rollout test 只有同时满足以下条件才可用于 7B 主结果：

1. 500～1,000 条，IID/Compositional/Challenge 覆盖达标。
2. 三个工具、追问、停止调用和无工具回复均有足够样本。
3. 所有 case 可在模拟器中执行，严重 oracle 错误为零。
4. 与训练集无父样本、文本和近重复泄漏。
5. 100～200 条双人独立复核完成并报告一致性。
6. Initial、简单规则基线和 oracle 能被评测器合理区分。
7. 版本、来源、代码和产物哈希完整可追溯。

在这些门槛之前，只能称为 development/evaluator test，不能在简历中写作正式任务成功率。
