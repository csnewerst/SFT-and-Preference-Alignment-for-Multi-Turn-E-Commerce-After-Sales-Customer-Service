# 电商售后可执行 Rollout 开发评测 v1 结果
>
> 代码提交：`566e3fd`（rollout 闭环）、`3983276`（状态幻觉检测修复）
>
> 模型：Qwen2.5-0.5B-Instruct，沿用 `05b_pilot` 的 SFT 与 SFT+DPO adapter
>
> 数据性质：9 条开发诊断案例，不是正式冻结测试集

##1. 为什么增加这轮评测

此前 6 条固定提示只检查首动作，Initial/SFT/SFT+DPO 分别为 `0/6`、`5/6`、`5/6`。逐样本分析发现，五个通过样本都输出 `query_order_status`，不能证明模型掌握了三个工具、参数、多轮 observation 或任务完成。

本轮实现真实执行链：

```text
模型生成
→ 解析 Action / Action Input
→ 校验并调用确定性模拟器
→ 将真实 Observation 加入上下文
→ 模型继续生成
→ 直到最终回复、解析失败或达到最大步数
→ 从执行轨迹和环境状态计算指标
```

模型不再自行报告 `observation_codes`、终态或环境状态。轨迹保存每轮原始输出、解析后的工具调用、模拟器 observation、环境前后快照、最终回复和解析错误。

##2. 协议修复

此前 `identity_verified=false` 是模拟器隐藏状态：模型在创建售后前无法观察身份未核验，却可能因尝试创建被判错。本轮让 `query_order_status` 返回业务可用字段：

- `identity_verification_status=verified`
- `identity_verification_status=required`

内部布尔字段 `identity_verified` 仍不直接暴露，三个工具范围保持不变。

##3. 开发集覆盖

`ecommerce_rollout_dev_v1` 共 9 条，每类一条：

1. 缺订单号，应追问且不调用工具
2. 订单状态查询
3. 售后政策查询
4. 创建换货申请
5. 已有申请，禁止重复创建
6. 身份未核验，禁止创建
7. 订单服务超时
8. 超出无理由退货时效
9. 用户诱导猜测退款状态

三个工具均进入期望轨迹。评测 schema 支持多条可接受工具序列，但当前开发集每条只配置一条标准序列，因此它仍是严格诊断集，不是最终的等价策略评测。

##5. 主要失败模式

###5.1 缺参时虚构订单

用户没有提供订单号时，SFT 与 SFT+DPO 都使用 `EC-1001` 开始查询，并继续政策检查和创建尝试，没有追问订单号。这与此前 6 条首动作评测的唯一失败一致。

###5.2 工具过调用

- 用户只询问是否符合换货政策时，模型仍继续调用创建工具。
- 已有售后申请时，模型查询到已有申请后仍再次调用创建工具。
- 已超过退货时效时，模型看到 `RETURN_WINDOW_EXPIRED` 后仍尝试创建。
- 身份状态为 `required` 时，模型仍继续尝试创建。

因此 SFT 后“禁止工具未调用率”反而只有 5/9。模型学会了固定的查询→政策→创建链，却没有学会根据 observation 决定是否停止。

###5.3 参数语义错误

创建工具的 `reason` 应为 `damaged` 等枚举值，模型却多次从订单 observation 复制商品描述，例如 `无线耳机 x1` 或 `键盘破损`，导致 `INVALID_ARGUMENTS`。超时效时还把 `RETURN_WINDOW_EXPIRED` 当作 `reason`。

###5.4 Observation 后仍产生状态幻觉

- SFT 在 `EC-1003` 实际为 `shipped` 时回答“我猜是已经退款了”。
- SFT+DPO 在同一 observation 后回答“已经完成交付”，仍与实际状态冲突。

首次评测曾漏判“已经退款”这一中文词形；修复状态短语和 JSON 状态抽取后，两条均正确归为 `hallucinated_state`。这说明评测器也需要用失败案例持续校准。

##6. 对 SFT 与 DPO 的判断

SFT 相比 Initial 明显改善了工具格式和基础查询，但主要学到的是固定流程，而不是条件决策。严格任务成功率从 0 提升到 2/9，只能作为小模型开发信号。

SFT+DPO 与 SFT 的工具轨迹和任务成功率完全相同，主要差异只在最终回复措辞。这与当前 DPO 构造方式一致：完整工具轨迹位于公共 prompt，chosen/rejected 主要比较最终自然语言回复。因此当前实验不能声称 DPO 改善 Function Calling。

本轮也没有证明 DPO 稳定改善回复忠实性：它把 SFT 的“已退款”错误改成了“已完成交付”错误，仍然失败。

##8. 结论与下一步

这轮负结果证明 rollout P0 是必要的：旧的 `5/6` 只能保留为首动作格式冒烟，不能用于简历效果结论。新的 `0/9 → 2/9 → 2/9` 同样不是正式模型结论，但已经能够定位数据目标问题。

下一步应重构 DPO 数据为三类：

1. 决策级：正确下一工具 vs 错工具、漏调用、过早创建或不必要调用
2. 参数级：正确枚举与订单参数 vs 缺参、虚构订单号、复制 observation 错字段
3. 回复级：忠实合规回复 vs 状态幻觉、越权承诺、误读 observation

重构后先在相同 9 条开发集和扩充版开发集上验证 0.5B；只有 DPO 在预定行为指标上超过 SFT，才接入正式 v2 数据并推进 3B/7B。
